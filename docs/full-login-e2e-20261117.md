# 로그인부터 PP 재활용 완료까지 재검사

2026-11-17, 로컬 Docker 통합 환경에서 확인했다. **개발용 로그인으로 별도 A·B·C 계정을 사용한 PP 두 경로는 실제 웹에서 끝까지 완료됐다.** Google·Microsoft 소셜 로그인은 앱 인증정보가 없어 검증하지 못했다. 따라서 운영 배포 전체를 완료했다고 보지는 않는다.

## 무엇을 실제로 눌렀나

화면 `http://localhost:5178` → 서버 8000 → 문진 8030 / 업체 검토 8010 → PostgreSQL을 연결했다. 문진과 업체 검토에는 설정된 Azure 모델을 실제 호출했다. 미리 정해 둔 성공 응답으로 화면만 넘기지 않았다.

기업·물량·수락·계량 근거는 모두 **로컬 합성 시험자료**다. 실제 업체 허가, 실물 운송, 실제 품질, 법정 재활용 인증을 확인한 결과가 아니다. QR은 화면에서 발급한 링크를 수신 기업 계정으로 열었다. 휴대전화 카메라의 광학 인식은 이번 범위에 포함하지 않았다.

## 단계마다 달라져야 하는 값

- A→B 검토: A의 사업장 위치, 제조 잔재 1,000kg, 최초 문진의 분류번호·R유형을 사용했다.
- B→C 검토: B 시험사업장 위치, **B가 기록한** 파쇄품 950kg, B 단계의 사진을 사용했다. 최초 R유형을 후속 산출물에 자동으로 재사용하지 않는다.
- A의 후보 14개, B의 후보 9개 모두 물량 AI 검토가 완료됐다. 업체 공개 근거가 충분한지는 별도 상태다. 14/14·9/9 검토 완료를 14개·9개 업체 모두 반입 승인으로 해석하면 안 된다.
- B→C 사진 검토는 보이는 조각·끈·색을 설명했고, 재질·순도·수분을 사진으로 확정하지 않았다. 공개 연구의 예시 사진임을 알아보고 실제 물량 사진과 시험자료를 요청했다.
- 지도는 현재 보유 기업 기준의 가까운 최대 5곳을 표시한다. 목록과 AI 검토는 전체 후보를 유지한다. 이번 거리 값은 **직선거리**이며 도로 운송거리·운송비 검증 결과가 아니다.

사진은 공개 Wageningen 보고서의 PP 예시를 사용했다: <https://edepot.wur.nl/518299>, Figure 6.1. 실제 시험 물량의 사진이나 품질 증명이라고 입력하지 않았다.

## 다른 소재도 확인했나

**18개 소재를 HTTP로 실제 문진 → 확정 → 분류번호·R유형 전달 → 형태별 경로 조회까지 검사했다.** 이 18개 전부를 브라우저로 인수·QR·완료한 것은 아니다.

- 18/18 문진의 예상 분류번호와 인계 결과가 일치했다. 이는 현재 규칙과 연결의 회귀 검증이며 법률 전문가의 정확도 검증은 아니다.
- 지원 소재의 형태 조회 56개 중 53개는 후보가 나왔고, 3개 PE·PS 베일 입력은 검수된 업체 근거가 없어 후보가 없었다.
- 페놀수지·PU폼·고무 3종은 분류 이후 처리경로 미지원으로 표시된다.
- 별도의 기준 DB 전체 조회는 212건: 후보 141, 근거 있는 다음 경로 없음 15, 경로 끝 56. 이 숫자는 실제 인수 요청 건수가 아니다.
- 실제 적재본은 시설 62곳 / 공정 전환 69개 / 시설·공정 연결 129개. 이번 소재 범위에서 124개 연결과 64개 전환에 도달했다. 나머지 5개는 이번 범위 밖 종이 공정이다.
- 위험 잔류물 조건 11개는 모두 일반 재활용 경로로 진행하지 않고 확인 보류됐다.

## 재검사에서 고친 것

1. **수락·입고 후에도 상단 단계가 예전 상태로 남는 문제**: 처리 건의 변경을 상세 페이지에도 전달한다. 등록 안내도 등록 직후 상태에만 남긴다.
2. **수신 업체 카드가 '상대 응답 대기'라고 말하던 문제**: 발송자/수신자와 요청/조건부/수락 상태를 구분해 지금 할 일을 표시한다.
3. **업체를 검색하면 다른 공정마다 잘못된 빈 결과 안내가 나오던 문제**: 검색에 맞는 업체가 있는 공정만 남긴다. 실제로 업체가 없는 원래 공정의 안내는 검색 전에는 유지한다.
4. **문진 첫 질문 성능 검사 실패**: 전체 검사에서 1.265초, 단독 재현에서 1.223초로 1초 기준을 넘었다. 소재 선택 전에는 사용하지 않는 확정·질문·증빙 집계를 만들지 않도록 수정했다. 후보와 근거·우선순위는 전체 평가와 동일함을 4개 회귀 사례로 비교했다. 수정 후 같은 로컬 환경 3회 측정은 0.808 / 0.868 / 0.839초였다. 일반적인 응답시간 보장 수치는 아니다.

5. **동시 문진에서 서버가 먼저 시간초과되는 문제**: 추가 통합 검사에서 PS·비철 스크랩·금속캔의 새 문진, EPS·고무의 위험조건 문진 총 5건이 server의 30초 대기를 넘겨 503으로 끝났다. diagnosis의 SDK 재시도와 오케스트레이터 재시도가 중첩되지 않게 했고, infra에서 모델 호출 60초·서버 대기 300초를 연결했다. diagnosis 준비 상태도 확인한 뒤 server를 시작한다. 실행 중인 컨테이너의 300초·60초·SDK 재시도 0회 설정도 확인했다. 이 수정은 처리 용량 보장이나 무제한 재시도가 아니다.

법 규칙·API·DB 스키마·수락 권한을 바꾸지 않았다. 처음 전체 문진 검사는 668 통과·성능 1 실패였고, 성능 수정 뒤 673개가 통과했다. 이후 통신 예산 검사 4개를 추가했다.

## 아직 완성으로 표시하면 안 되는 부분

- 소셜 로그인: Google·Microsoft 앱 설정과 콜백 주소를 실제 배포 환경에 연결한 뒤 로그인·로그아웃·재로그인을 다시 시험해야 한다.
- 미지원 소재와 PE·PS 베일 등 공개 반입 근거 부족 경로: 업체를 임의로 추가하지 않았다. 근거 확보와 업체 연결이 필요하다.
- 수신 계정 연결은 시험용이다. 실제 업체 회원 확인과 현재 반입조건을 갖춘 운영 검증은 별도다.
- 업체 AI 검토는 조건 확인을 돕는 검토다. 가격·도로 운송거리·법정 인증·수용량까지 모두 확정한 추천이 아니다.

## 재현 자료

로컬 워크스페이스의 `output/verification/full-login-e2e-20261117/`에 HTTP 검사 스크립트, 결과 JSON, 실제 AI 검토 응답, 화면 증빙을 보관했다. 인증 쿠키·API 키·QR 토큰은 보고서에 포함하지 않는다.

주요 파일: `validation-summary.json`, `auth-live.json`, `diagnosis-routes.json`, `catalog-audit.json`, `hazard-holds.json`, `handoff-access.json`, `chain-processing-gates.json`, `chain-stage-a-review.json`, `chain-stage-b-review.json`, `chain-final.json`, `chain-final-proof.jpg`, `chain-final-latest-ui.jpg`.

서비스 재빌드 도중 끊긴 첫 위험조건 검사는 `hazard-holds-interrupted-by-rebuild.json`으로 보존했고, 안정화 후 다시 실행한 `hazard-holds.json`의 11개가 모두 통과했다.

동시 호출에서 시간초과가 발견된 결과는 `diagnosis-routes-final.json`, `hazard-holds-final.json`에 남겼다. 설정과 SDK 재시도 수정 후 통과한 5건은 `diagnosis-timeout-retest.json`, `hazard-timeout-retest.json`이다.
