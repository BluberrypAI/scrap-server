# 문진부터 업체 검토까지 R코드가 이동하는 방법

사용자가 문진을 확정하면 분류번호로 별표 4의3의 재활용 유형을 조회합니다.
화면에서는 `재활용 유형 확인`을 펼쳐 유형과 분석 조건, 원문을 볼 수 있습니다.

1. **diagnosis**: 일반 플라스틱·금속 14개 분류번호의 유형을 표에서 읽습니다. R-10의 분석 조건을 보존합니다.
2. **server**: 로그인 기업의 확정 문진인지 확인하고 번호·판정 버전·법 기준일을 대조합니다.
3. **web**: 업체 후보와 함께 유형표를 표시합니다. 사용자가 R코드를 다시 입력하지 않습니다.
4. **물량 등록**: 최초 분류, 유형표와 출처를 저장합니다. 기존 확정 문진은 원래 판정을 고치지 않고 보충 조회합니다.
5. **route AI**: 후보 전체에 유형표·분석 조건·원문 링크를 전달하고 실제 업체의 공정·재질·현재 형태를 검토합니다.
6. **B의 처리 후**: 실제 산출물로 다음 공정을 찾습니다. A의 분류/R유형을 C 인계에 자동 재사용하지 않습니다.

## 무엇이 확인된 것인가요?

`표 등재`는 이 분류번호의 법령표에 해당 유형이 있다는 뜻입니다.
해당 업체의 현재 허가, 이 물량의 분석 결과, 인수 승인을 뜻하지 않습니다.
`사전 분석 해당 없음`도 모든 검사·확인을 생략해도 된다는 뜻이 아닙니다.
R-10은 뒤에 어떤 유형으로 재활용할지에 따라 분석 조건이 달라집니다.

실제 업체 허가 대조는 여전히 별도 확인이 필요합니다. 수신 업체가 물량을 최종 수락합니다.
분류가 미확정·지정폐기물·지원 밖이면 일반 업체 추천으로 우회시키지 않습니다.

## 팀 적용 순서

scrap-diagnosis #23과 scrap-server #47, scrap-route #61, scrap-web #46을 함께 적용합니다.
추가 필드만 사용하므로 이전 문진은 보존됩니다. 기존 AI 검토는 R유형을 포함해 다시 검토해야 합니다.
infra에서 `docker compose up -d --build` 후 `docker compose run --rm server-seed`를 실행합니다.
DB 마이그레이션은 추가되지 않았습니다. 서버와 seed는 같은 이미지를 써야 합니다(infra #5).

## API 필드

- 건 상세 GET: `handoff.recycling`(확정 시점), `recycling`(기존 판정에 대한 보충 조회).
- treatment context: `recycling`, `route_input.recycling_types`, `route_input.recycling_basis`.
- 물량: `data.recycling`, `data.initial.recycling_types/recycling_basis`.
- AI 후보 패킷: `recycling_types`와 `recycling_basis`(법 출처만, 기업·문진 식별자 제외).
- AI 검토 캐시: `recycling_checksum`. 자료 변경·누락 시 이전 검토로 인수 요청하지 못합니다.

최상위 보충 조회는 서버가 엔진에서 읽습니다. 브라우저가 제출한 법령 출처를 신뢰하지 않습니다.
기존 `/api/treatment` 검색 API의 R유형은 검색 문맥이며, 엔진 조회 출처로 승격하지 않습니다.
