# 처리 결과 통합 등록·A 카드 갱신 검증

2026-11-20, T-183. 로컬 통합 Docker에서 확인했다. [명세](specs/output-disposition-card-sync.md), [정리된 API 결과](verification/output-disposition-20261120.json).

## 변경

`/output` 한 요청으로 실제 산출물과 다음 진행(complete/forward/hold)을 함께 저장한다. 완료 허용 형태·예정 산출물 일치·현재 기업·revision·근거·용도·확인을 모두 통과해야 완료한다. 실패하면 산출물과 진행 상태를 부분 변경하지 않는다. 기존 필드는 유지하고, 새 필드를 보내지 않는 클라이언트는 종전 processed 동작을 유지한다.

보관 중은 stored이며 후보 조회·검토·인계를 차단한다. `/output-action`에서 다음 진행만 바꿔 재개하므로 산출물/공정을 중복 기록하지 않는다. 기존 `/finish`는 호환용으로 남고 새 웹은 사용하지 않는다. DB 마이그레이션과 환경변수 추가는 없다. 웹 PR #68과 함께 적용한다.

## 실제 확인

| 시나리오 | 결과 | QR 입고 / 산출물 기록 | 카카오 자동차 도로거리 |
| --- | --- | --- | --- |
| A→B | PET병 100kg → 새롬 화성 제1공장 플레이크 90kg, 결과 등록에서 완료 | 1 / 1 | A→B 11.229km |
| A→B→C | B 플레이크 90kg 보관 → 같은 결과를 추가 가공으로 변경 → 디와이폴리머 평택 QR 입고 → 펠릿 85kg 결과 등록에서 완료 | 2 / 2 | A→B 11.229km, B→C 37.350km |

완료 두 건을 A 계정에서 확인했다. 두 번째 건의 보관·추가 가공 이력이 유지되고 산출물 기록은 두 개뿐이다. A 목록을 열린 채로 둔 상태에서 B→C 인수 요청을 발생시켰고, 수동 새로고침 없이 C가 세 번째 사업장으로 표시됐다. 완료 시 기존 완료 이력으로 이동한다.

**시험 범위:** B 결과 등록/다음 진행 선택, C 수락, B 운송·QR 발급, C QR 입고·최종 결과·완료, A 조회는 브라우저로 조작했다. A→B 입고까지는 실제 문진·검토·인계 API로 준비했다. A 카드 갱신 시험의 B→C 요청은 A 화면을 유지하기 위해 별도 HTTP 세션에서 실제 API로 보냈다. 가입부터 전부 웹으로 검증했다는 뜻은 아니다. 공개 업체 자료를 사용했지만 계정 연결·물량·성상·완료 근거는 합성이며 실제 업체 연락·운영 배포는 하지 않았다. 경로는 계산된 자동차 경로이며 실제 차량 GPS가 아니다.
